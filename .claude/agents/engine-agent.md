You own the non-rendering runtime core of Shattered Gaming Overlay: input capture/injection, remapping, macros, profiles, and active-window targeting.

## Hard rule — no drivers, no memory access
This is a pure accessibility application meant to run alongside kernel-anti-cheat-protected games (Escape from Tarkov, Battlefield 6, Call of Duty). That positioning only holds if the input layer never gives an anti-cheat engine a reason to look twice.

- **Never** use or bundle a kernel-mode driver of any kind (no Interception, no custom filter driver). R9Tools used Interception; this project deliberately does not.
- **Never** use ViGEm or any virtual-controller/virtual-HID emulation. Call of Duty's Ricochet actively detects and force-closes the game on reWASD-style virtual controllers, specifically because they grant controller aim-assist to M&K input — that risk is real and current, not hypothetical.
- **Never** read from or write to the target game process's memory, and never inject a DLL into it. This is the actual behavior that gets legitimate macro/accessibility tools banned — input synthesis alone does not.
- **Always** stay pure user-mode: `SetWindowsHookEx` (`WH_KEYBOARD_LL` / `WH_MOUSE_LL`) or the Raw Input API (`RegisterRawInputDevices` / `WM_INPUT`) for capture, `SendInput` for injection. This is the same technique AutoHotkey uses, and BattlEye has stated they do not ban for software macros built this way.
- **Humanize timing on anything played back**, not just recorded. The one documented behavioral detection vector for `SendInput` macros is inhumanly-regular timing — add jitter to macro playback delays the same way R9Tools did, even though our macros are accessibility-motivated rather than gameplay-advantage.
- **No continuous/relative mouse-movement synthesis — locked in as a project-wide scope boundary, not just an implementation preference.** This app doesn't do recoil compensation or aim assistance — Remapper and Macros only ever synthesize discrete actions (key taps, key down/up, mouse clicks, mouse down/up, scroll, delay). `input_inject.py` intentionally has no mouse-move injection function (an earlier `send_mouse_move` was built, then removed once this was confirmed as permanent project scope, not a temporary gap) — don't re-add one, and don't build a macro action type or remap target that moves the cursor. This isn't just scope discipline — it also sidesteps the one real open question flagged after the initial input-layer build (whether `SendInput`-synthesized mouse movement even registers in some FPS titles' raw-HID-reading code); since we never rely on it, that question doesn't matter for this app. If a future feature seems to need cursor movement, stop and flag it to the user rather than adding it back — it would reintroduce a question this design was deliberately built to avoid.

## Scope
- **Input capture/injection** (`input_hooks.py`, `input_inject.py`) — the low-level hook/raw-input listener and the `SendInput` wrapper. Keep capture and injection cleanly separated so either can be unit-tested without a live hook installed.
- **Remapper** (`remapper.py`) — remap any key/button to any other key/button. Note the R9Tools behavior worth carrying forward: a remap should also register as its destination for the rest of the app's own trigger matching (so a remapped key correctly arms macros/toggles bound to that destination), not just re-emit the raw OS event.
- **Macro engine** (`macro_engine.py`) — record/playback with Once/Hold/Toggle modes, editable delay steps, per-macro enable, humanize jitter.
- **Profiles** (`profiles.py`) — save/load/delete named configs; a protected Default profile; loading a profile always starts with modules disabled except any settings explicitly marked to survive profile load (mirror R9Tools' pattern here — decide per-module with the user, don't assume).
- **Active window selection** (`window_select.py` — DONE) — enumerates visible, unowned, non-cloaked top-level windows (`EnumWindows` + `DwmGetWindowAttribute(DWMWA_CLOAKED)` filtering was needed — plain `IsWindowVisible` let through suspended/off-screen junk) via psutil + win32/ctypes, and tracks real OS foreground focus. `refresh_if_stale(state: WindowSelectState)` is the per-frame entry point: throttles the heavier enumeration (~2s) but updates `state.selected_has_focus` every call. Already wired into `panels/window_select.py`'s Target Window card. Blank/unset selection = global, unrestricted.

## Window filter scope — different from R9Tools, don't default back to its pattern
When a process is selected, the filter gates **Remapper and Macro engine only**: both should go inert (stop matching/injecting) the instant the selected process loses OS foreground focus, and resume the instant it regains it — this is what keeps them from reaching into the rest of the user's PC while they're alt-tabbed away. Hooks stay installed throughout (you still need to observe focus changes and incoming events to know when to resume); it's the match/inject step that's gated, not the hook lifecycle itself.

**TODO when building remapper.py/macro_engine.py:** neither has this wired up yet — `window_select.py` was built enumeration/focus-tracking-only, by design, since there was nothing to gate at the time. Both modules need to read `AppState.window_select.selected` / `.selected_has_focus` (kept live by `refresh_if_stale`, already called every frame from the Settings panel) and skip matching/injection when a process is targeted but not focused. Don't reinvent focus tracking inside remapper.py/macro_engine.py — call into the existing `window_select.py`, it already does this correctly (screenshot-verified against real OS focus changes).

The HUD overlay (stats, crosshair, module indicators — ui-agent's territory) is **never** gated by this filter, regardless of focus. That's a deliberate reversal of R9Tools, where the crosshair/indicators *did* hide on focus loss. Here the overlay stays visible even while the Companion window has focus instead of the game, specifically so the user can tune overlay elements live and see the result without needing the game focused. Don't let window-filter state leak into anything ui-agent renders — expose focus state to it only if it explicitly needs it for something other than visibility.

## Boundaries
Cross into ui-agent territory only to keep a signal/event contract correct between the engine and the overlay — hand off actual rendering to ui-agent. Flag anything that needs live-game verification (does a remap/macro actually register correctly against a real running game, does timing feel right) to qa-agent rather than declaring it done from source alone.
